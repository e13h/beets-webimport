# 24: Candidate review's cover-art preview shows a false "unavailable" error that doesn't retry

Status: ready-for-agent

**Category:** bug
**Source:** UX walkthrough session (Playwright MCP, browser-driven, per
ADR-0009). Reporter-suggested severity: High.

## What was observed

The candidate review view showed "art service unavailable — try again" as
static text (not an actual retry button/action) for the correct Mulan
candidate. Moments later, the same album's art rendered correctly in the
Library grid after a full page reload — the underlying fetch had actually
succeeded shortly after the error was shown.

Per `docs/agents/dev-environment.md`'s "fetchart specifics" section,
CAA/archive.org return transient 502s regularly, and the backend fetchart
path (`coverart.py`) already retries and reports an `unavailable` flag
rather than treating a transient failure as fatal. This finding suggests
the review-preview endpoint (which computes **Resolved Art** — see
`CONTEXT.md`) either doesn't share that retry logic, or the frontend
doesn't poll/re-request it the way it should.

## Why it matters

This is a false negative in exactly the feature (dual cover-art preview,
Source Art vs. Resolved Art match/mismatch) the spec calls out as a
first-class differentiator from beets-flask. A user acting on "art
unavailable" as if it were permanent could make a worse decision (e.g.
drag in manual art unnecessarily) than if the transient nature were
surfaced.

- `.playwright-mcp/06-library-after-import.png` — broken/missing-art render

## Reproduction

1. Start an import review, force the target MBID
   (`a5483fb3-634b-4254-a966-de33cefd1f17`) via search-by-ID.
2. Observe the candidate card's Resolved Art slot — it will sometimes show
   the "unavailable" message on first render.
3. Apply the import anyway, then reload the Library tab shortly after: the
   real art is present, proving the initial message was a transient false
   negative.

## Agent Brief

**Category:** bug
**Summary:** Auto-retry candidate review cover-art preview on transient 502/503 errors with visual spinner feedback and manual retry fallback

**Current behavior:**
When Cover Art Archive / archive.org returns transient 502/503 errors during candidate review art preview, the UI renders static text ("art service unavailable — try again") with no retry action or polling mechanism, resulting in false negatives even though the backend apply path retries and fetches art successfully.

**Desired behavior:**
1. **Auto-retry with exponential backoff:** When an art preview request fails with a 502/503 or network error, the frontend automatically retries the preview request up to 2 times (e.g. after 1.5s, then 3s).
2. **Visual retry feedback:** During retry attempts, the thumbnail loading spinner gives active visual feedback (e.g. status text "Retrying art lookup (1/2)..." or a brief pause/flash indicating a retry is in flight).
3. **Manual fallback action:** If all auto-retries fail, display an explicit, clickable "Retry lookup" button on the thumbnail card so the user can re-trigger art resolution manually once network connectivity clears.

**Key interfaces:**
- `app.js`: `openReview` candidate art preview fetch logic and retry loop.
- `style.css`: `.art-preview-retry` button and retry status styling.

**Acceptance criteria:**
- [ ] Transient 502/503 errors on candidate art preview trigger up to 2 automatic retry attempts.
- [ ] The loading indicator displays clear visual feedback when an auto-retry is occurring.
- [ ] If art resolves on retry, the cover image and Source/Resolved match indicator render normally.
- [ ] If all auto-retries fail, a clickable "Retry lookup" button appears on the card.
- [ ] Clicking "Retry lookup" restarts the art resolution attempt.

**Out of scope:**
- Backend fetchart algorithm changes.
